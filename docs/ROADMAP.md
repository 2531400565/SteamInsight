## P0 · 分享给朋友之前建议做

### P0-1　一键连通性自检（网络诊断面板）

**为什么第一优先**：这是当前**用户困惑的唯一来源**，而且我们已经有现成的判定逻辑了。

应用完全依赖外部网络（5 个域名），但界面上没有任何地方能告诉用户"现在到底通不通、不通是为什么"。
出问题时用户只能看到一句同步失败，然后自己猜。而实际情况是：

| 现象 | 真实原因 | 用户会怎么猜 |
| --- | --- | --- |
| 封面能显示、同步必失败 | hosts 被劫持但加速器退出了 | 「接口坏了 / 被封了」 |
| 全部失败 | 系统代理指向已退出的端口 | 「软件有 bug」 |
| 只能看演示数据 | 没填 API Key / 隐私不是公开 | 「拉不到数据」 |

这三种的**处置方式完全不同**，但界面上长得一模一样。

**落点**：设置页加一张卡片，主进程新增一个 IPC 通道，复用 `electron/main/http.ts` 的 `fetchText`
与 `proxyLabel`，逐个请求 5 个域名，把 `via / status / 耗时 / error` 原样显示，并附**结论与处置建议**。
判定逻辑我已经跑通并在 `tools/probe-net/` 里验证过（见 `docs/DEPLOY-AND-NETWORK.md` 第四节），
直接搬进主进程即可，不需要重新设计。

建议直接给出的人话结论，例如：

```
✅ 网络正常（加速器在跑，走直连）          5/5 通
⚠️ 加速器似乎没在运行：Steam 域名被解析到 127.0.0.1 但无人应答
   → 请打开 Steam++ / Watt Toolkit，或在加速器里点"还原 hosts"
⚠️ 系统代理指向 127.0.0.1:7897，但该端口没有程序在监听
   → 请重开代理客户端，或关闭「设置 → 网络 → 代理」里的手动代理
```

**顺带收益**：`features.len 5` 的探针已经写好，接 UI 的成本比从零做一个诊断功能低得多。

**规模感**：小-中（主进程 ~80 行 + 一张卡片 UI）。

### P0-2　本地日志 + 崩溃捕获 + 一键导出诊断包

**为什么**：**当前项目完全没有日志落盘。**

全文检索 `electron/main/*.ts`，`fs.writeFile` 只有 4 处，全是写数据库 / 设置 / 导出文件 ——
**没有任何一行写日志**。同时 `index.ts` 里也没有 `process.on('uncaughtException')` 之类的兜底。

后果：朋友用的时候报错，他只能截图给你，而**你没有任何可查的东西**。
这个项目里已经出现过好几次"静默失败"了 —— 托盘图标不显示（`createEmpty()` 不抛错）、
成就名全空（字段名写错但接口 200）—— 都是靠额外取证才挖出来的。

**落点**：
- 主进程加一个极简 logger：`%APPDATA%\steam-insight\logs\app-YYYY-MM-DD.log`，按天滚动，保留 7 天。
- 同步的每个阶段、每次网络请求的 `via/status/error` 都记一行（这些信息 `http.ts` 已经在返回里了，现成的）。
- 加 `process.on('uncaughtException')` / `unhandledRejection` 落盘，避免"直接消失"。
- 设置页加「导出诊断包」按钮：打包日志 + `settings.json`（**必须脱掉 `steamApiKey`**）+ `appInfo`。

> ⚠️ 脱敏是硬要求：`settings.json` 里有明文的 API Key，导出前必须打码或剔除。

**规模感**：小（logger ~60 行 + 2 个 hook + 1 个导出动作）。

### P0-3　代码签名（消除 SmartScreen 蓝色拦截框）

**为什么**：现在**产物是完全未签名的**，实测 PE 证书表大小为 0（`docs/DEPLOY-AND-NETWORK.md` 第三节）。
朋友双击安装会撞「Windows 已保护你的电脑」，必须点「更多信息 → 仍要运行」。
微信 / QQ 传的 exe 更容易被拦，甚至可能被当作风险软件劝退。

**选项**：

| 方案 | 效果 | 代价 |
| --- | --- | --- |
| OV 代码签名证书 | 消除 SmartScreen（需累积下载量） | 约 ¥1000-2500 / 年，要企业或个体资质 |
| EV 证书 | 立即获得 SmartScreen 信誉 | 更贵，要硬件令牌 |
| 自签名 + 手动信任 | 只有你自己那台机器有效，别人照样被拦 | 免费但基本没意义 |
| **不签，提前说明** | 0 成本 | 每次都要跟朋友解释一遍 |

**如果只是想内部几个人用，选第 4 个就够了** —— `docs/DEPLOY-AND-NETWORK.md` 里已经写好了一段
可直接复制给对方的话。要往外发才值得考虑买证书。

**规模感**：无代码改动；`electron-builder.yml` 加 2 行配置。

## P1 · 高性价比（体验 / 性能）

### P1-4　商店侧同步加 TTL，别每次全量重拉

**为什么（有具体位置）**：`sync.ts:65`

```ts
await pool(owned, 4, async (g) => { storeCache.set(g.appId, await storeAppDetails(g.appId).catch(() => null)) })
```

这一句在 `buildApiData()` 里，**每次同步都对整个游戏库重拉一遍商店详情**（分类 / 标签 / 价格 / 好评率），
没有任何过期判断。库容 N 时，每次同步 ≈ N 次请求，愿望单再加 M 次。

对照一下：**成就侧已经做了增量**（`achievement-sync.ts`，只拉"本次玩过"或"库里没记录"的，
注释里还留了实测数据：全量 69 款 ≈ 207 请求 / 约 18 秒）。**商店侧没有同类处理 —— 两边不对称。**

量级感受（默认 `autoSync=true` / `syncIntervalMin=30`，即一天 48 次）：

| 库容 | 每天 appdetails 请求数（仅游戏库部分） |
| --- | --- |
| 69 款（本机实测库容） | ≈ 3,300 |
| 500 款 | ≈ 24,000 |

**落点**：`games` 表已经有 `price_checked_at` 字段，可以直接当 TTL 依据。建议：
- 游戏库 appdetails：TTL 6~24 小时；
- 愿望单 / 折扣专区：仍每次刷（这些才是"要变的信息"）；
- 用户手动点「立即同步」时强制绕过 TTL。

顺带一提：商店接口没有公开配额，但高频重拉会被限流；而且首次同步对 500 款的库会明显慢。

**规模感**：小（一个 TTL 判断 + 手动同步的 `force` 选项）。

### P1-5　补 `app.setAppUserModelId`

**为什么**：全文检索 `electron/main/*.ts`，**没有任何一处调用 `app.setAppUserModelId`**。
Windows 上 Electron 的 `new Notification()` 需要 AppUserModelID 才能正确显示**应用署名与图标**
（`notifications.ts:32`）。

从快捷方式启动时，NSIS 会把 AUMID 写进快捷方式、Electron 能推导出来，所以大概率没问题；
但**免安装版直接双击 `Steam Insight.exe` 启动时**，通知可能署名成 Electron、任务栏分组也可能不对。
而免安装版恰好是你自己调试时最常用的启动方式。

`electron-builder.yml` 里已经有 `appId: com.steaminsight.desktop`，直接对齐即可。

**规模感**：极小（1 行）。

### P1-6　价格阈值提醒

**为什么**：基础设施**全都在，只差一个阈值配置**。
现有：`price_history` 表（`schema.ts:121`）每次同步追加采样、`PriceLineChart` 已经有折线图、
通知通道 `notify()` 已通、跨重启去重机制 `notify-plan.ts` 也做好了（靠 `notified_at` 落库）。

现在能提醒的只有「愿望单打折」「史低」「限时免费」三类**固定规则**。加一条
「**降到 ¥X 以下通知我**」，是用户对折扣工具最自然的期待。

**落点**：`settings` 加一个 `priceAlerts: { appId, thresholdCents }[]`；
`notify-plan.ts` 加一条判定（现有 `planNotifications` 已经是纯函数，好扩展）；
愿望单页加一个"设个心理价"的输入。

**规模感**：小-中。

## P2 · 功能扩展

### P2-1　周报 / 月报

`WrappedPage` 已经做了年度回顾，并且 **PNG（截图）与 PDF（`printToPDF`）导出链路已通**
（`exporter.ts:88`）。把同一套渲染扩到"上周 / 本月"，可分享性很强 —— 这是这类工具最容易被转发的形态。
**规模感**：中（主要是排版，导出复用）。

### P2-2　成就追猎清单

数据层已经齐了：`Achievement.globalPercent` + `isRare`（`achievement-sync.ts:68` 已按"全局占比 < 10% 且已解锁"判定稀有）。
可以再进一步：把「**稀有 + 尚未解锁**」做成一个待办清单（"还差 3 个稀有成就"），配合每日提醒。
**规模感**：小-中（一个新页面 + 一个通知规则）。

### P2-3　托盘右键菜单增强

现在只有三项：显示主窗口 / 立即同步 / 退出（`notifications.ts:47`）。
建议加「上次同步时间 · 下次同步倒计时」（非点击项，纯展示）、「打开愿望单」。
数据现成（`sync.getSyncStatus()`），改动极小但日常体感提升明显。
**规模感**：极小。

### P2-4　数据包导入 / 导出

现在**只能导出不能导入**：`exporter.ts` 支持 CSV / XLSX / PNG / PDF，但没有任何导入入口。
加一个「导出数据包 / 导入数据包」（带版本号的 json 或直接拷 db 文件），能解决三件事：
换机迁移、重装前备份、多台电脑之间同步分析结果。
**规模感**：中（要设计格式 + 版本兼容 + 冲突策略）。

### P2-5　家庭共享库识别 —— 调研结论：**当前认证模型下不可行，不实现**

**结论：接口存在，但本应用拿不到它需要的凭据。** 因此按「不承诺」处理，明确不做。

调研依据（2026-09-26 核实）：

| 事实 | 详情 |
| --- | --- |
| 接口确实存在 | `IFamilyGroupsService/GetSharedLibraryApps/v1/`，返回 `response.apps[]`，每项含 `appid` / `owner_steamids` / `exclude_reason` / `rt_playtime` 等字段，`exclude_reason === 0` 即可正常共享 |
| **但它要的是 `access_token`，不是 API Key** | 调用形如 `…?access_token=<token>&family_groupid=<id>&include_own=true`。**Web API Key 无效** —— 两者是 Steam 上完全不同的两套凭据 |
| 还需要先拿 `family_groupid` | 先调 `IFamilyGroupsService/GetFamilyGroupForUser/v1/?access_token=<token>` 才有 group id，等于要串联两步鉴权 |
| 属**未公开**接口 | 不在 Steamworks 公开 Web API 文档里（官方文档站只到 SDK / 商店概要层），靠社区逆向（XPaw / AugmentedSteam #1907）维护，随时可能变 |

**为什么本应用做不到**：当前认证是两条路 —— **Web API Key**（`steamcommunity.com/dev/apikey`，免费、用户可自助申请）与 **OpenID**（走系统浏览器，只用来确认 SteamID64）。两条路**都产不出 `access_token`**。access_token 属于 Steam 客户端 / OAuth 令牌体系，要么让用户去抓客户端凭据（等于教用户做危险操作），要么自建 OAuth 流程（PRD §5 明确反对在应用内碰账号密码）。

**因此维持现状**：只显示 `GetOwnedGames` 的**自有**游戏库。这也与 PRD §5 的硬约束一致 —— 宁可少显示一类数据，也不用需要用户交出额外凭据的方式去凑。UI 上不再提「家庭共享」字样，避免让用户误以为漏了数据。

> 若将来 Steam 把这个接口转正并开放 key 鉴权，再回来评估。

## P3 · 工程债与小事（不影响使用，但该收）

| # | 项 | 实况 | 建议 |
| --- | --- | --- | --- |
| P3-1 | **自动更新** | 没装 `electron-updater`。每改一点都要重新发一份 117 MB | 若打算长期分享，值得上；需要找个静态托管 |
| P3-2 | **多账号隔离** | `settings` 只存一个 `steamId`。`users` / `play_sessions` / `wishlist` 带 `steam_id`，但 **`games` 表没有** —— 它按 `app_id` 单键存，换账号后游戏库会互相覆盖 | 要么在 UI 里讲明"只支持单账号"，要么给 `games` 加 `steam_id`（改动大，要连带改 repository 与 queries） |
| P3-3 | **`private: true` 与 MIT 的张力** | `package.json` 写 `license: MIT`，但**仓库里没有 LICENSE 文件**，同时 `private: true` | 要开源就补 LICENSE，要内部用就把 license 字段改掉，别让它含糊 |
| P3-4 | **文档小瑕疵** | README 写「9 个页面」，PRD §7.1 写「10 个页面」（侧边栏实际 8 项 + 游戏详情 + 欢迎页 = 10） | 统一口径 |
| P3-5 | **注释与默认值不一致** | `achievement-sync.ts:7` 注释写「默认每 15 分钟自动同步」，而 `DEFAULT_SETTINGS.syncIntervalMin = 30` | 改成 30，或把默认值改成 15 |
| P3-6 | **根目录残留** | `electron.vite.config.1790411952977.mjs` / `...824086.mjs` 两个文件 | 已被 `.gitignore` 的 `electron.vite.config.*.mjs` 忽略，属 electron-vite 加载 TS 配置的副产物；会累积，可顺手清 |
| P3-7 | **PRD §7.2 的"未验证项"可以补** | 通知弹窗、导出 PNG/PDF 落盘、拉起 Steam 三项标注"未验证" | 现在这台机器有真实桌面会话，逐项走一遍就能把它们从"未验证"转成"已验证" |

## 明确不建议做的

| 项 | 为什么不做 |
| --- | --- |
| **自建"每日游玩时长"数据源 / 引入第三方史低数据** | Steam 官方 API 不提供每日时长，第三方史低源也不可靠。PRD §5 已经把这条写成硬约束 —— **宁可显示"需要积累"也不要用看起来像的数据糊过去**。这是这个项目最值得保持的品质 |
| **把 SQLite 换成联网后端** | 会让"无需账号、数据不出本机"这个优点消失，且给分享增加一整套部署成本 |
| **自己实现 Steam 登录（输账号密码）** | 已有 OpenID 走系统浏览器，安全模型正确。任何"在应用内输 Steam 密码"的做法都是倒退 |
