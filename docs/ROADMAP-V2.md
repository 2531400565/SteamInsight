## 0. 一句话结论

V1 之后项目**功能面已经饱和**，但审计暴露出两个**被忽略的角落**：

1. **`price_history` 每次同步无脑追加，且永不清理** —— 实测已 1362 行，按默认 30 分钟同步推算 **约 131 万行/年**；`snapshots` 同样 **约 121 万行/年**。
2. **`PriceLineChart` 是死代码** —— 采了 1362 条真实价格历史，**界面一次都没画过**；全库 `grep` 找不到任何渲染点。

以及一个**第一印象问题**：实测 `play_sessions = 0`，新装用户同步完 69 款游戏、4392 小时累计时长，**游戏分析页 4 张图全是空状态**。

## Tier 0 · 真隐患（会随时间恶化，建议优先）

### N0-1　`price_history` / `snapshots` 没有保留策略 → 一年上百万行

**实测数字**（`tools/db-size.mjs`）：

| 表 | 当前行数 | 每次同步新增 | 30 分钟同步 → 每天 | 一年 |
| --- | --- | --- | --- | --- |
| `price_history` | **1362** | **75 行**（games 63 + wishlist 2 + discounts 10） | **3,600 行** | **≈ 131 万行** |
| `snapshots` | **1380** | 69 行（每款游戏 1 行） | **3,312 行** | **≈ 121 万行** |

采样密度实测：`price_history` 里每个 app_id 已有 **21 次采样**，跨 **5.4 小时**。

**为什么现在没炸但迟早会炸**：

- `repository.ts:151` 的注释明确写着「price_history / snapshots **不清理**：它们是与促销周期无关的长期采样」。
  `purgeStale()` 只覆盖 games / achievements / wishlist / discounts 四张表。
- `repository.ts:194` 的 `loadSnapshot()` 是 **`SELECT * FROM price_history`** 整表返回 ——
  渲染层每次 reload 都全量走 IPC。现在 3.5 万字符还无所谓，**一年后就是数十 MB**。
- `sync.ts:209` 的史低判定对**每个采样**调用一次 `repo.priceLowest(appId)`，一次同步 75 次。

**建议做法**：按时间**降采样**，而不是删除。

- 90 天内保留**全部**采样（史低判定要精确，这是 `isHistoricalLow` 的唯一依据）；
- 90 天以上只保留**每天一次的收盘价** + **该游戏历史最低那一笔**（保证 `priceLowest()` 永远算得对）；
- `snapshots` 只需保留**每款游戏最近 2 条** —— 它的唯一用途是「与上次快照做差分」（`sync.ts:135 lastSnapshot()`），
  更早的快照**从来没有被读过**，纯占体积。
- 落地：加一条 `SCHEMA_VERSION 2 → 3`（不需要改 DDL，只加一个清理函数 + 在 `persist()` 末尾调用）。

**规模感**：小-中（一个清理函数 + 一次迁移号 + 断言）。

### N0-2　`PriceLineChart` 是死代码：数据准、图表现成、就是没接上

**证据**：

```
$ grep -rn "PriceLineChart" src --include="*.tsx" | grep -v "charts/PriceLineChart.tsx"
（无输出）
```

- `src/components/charts/PriceLineChart.tsx` **存在且完整**（83 行，含最低点标记 `ReferenceDot`、`activeDot` 交互）。
- 它唯一的投影数据 `price_history` **已经在库里躺着**（1362 行，已按 `captured_at ASC` 排好序，
  `isHistoricalLow` 标记现成 —— 见 `src/database/queries.ts:23`）。
- 而游戏详情页目前只在 **`GameDetailPage.tsx:234`** 用**一行文字**显示「商店现价」。

**结论**：这是「**最后一公里**」—— 数据侧全通，只差把组件挂上去。

**建议做法**：`GameDetailPage` 的「月度趋势 / 每年累计」那一行旁边，加一张**「价格走势」**卡片，
把 `snapshot.priceHistory.filter(p => p.appId === game.appId)` 喂给现成的 `PriceLineChart`。
顺带在图上标注「历史最低 ¥X」与「当前现价」，把 `StorePage` 那套「史低是本机口径」的说明复用过来。

**规模感**：极小（~20 行 JSX，组件与数据都不用动）。

## Tier 1 · 立刻可做（数据已齐，零新采集）

### N1-1　库价值与性价比分析　⭐ 最推荐

**实测数据覆盖度**（`tools/db-audit.mjs`）：

| 口径 | 实测值 |
| --- | --- |
| 有价的游戏 | **51 款**（另有 12 款免费、6 款未获取） |
| 库当前商店价合计 | **¥5,225.80** |
| 库原价合计 | **¥7,410.90** |
| **平均折扣率** | **25.2%**（其中 **18 款正在打折**、33 款是原价） |
| 累计总时长 | **4,392.4 小时** |
| **每元每小时** | **0.841 h/元**（按当前价）/ 0.593 h/元（按原价） |
| 买了零时长 | **11 款**（最贵的：Warhammer: Vermintide 2 ¥108、RPG Maker XP ¥92、Dead Island: Riptide ¥74） |

**为什么值得做**：`games.price_cents` / `original_price_cents` **每次同步都在拉**（`sync.ts:112-113`），
但全库维度**完全没被利用** —— 只在详情页露过一次。这是纯「把已有数据变现」。

**建议给的东西**：

- 库当前商店价合计 / 原价合计 / 平均折扣率；
- **每元每小时**（把「4392 小时 ÷ ¥5226」这个数字讲成人话：「你这份库的性价比是每花 1 元玩 0.84 小时」）；
- **最划算 TOP N**（时长 ÷ 现价 最高）；
- **沉没成本清单**：买了、现价最贵、**一次没玩**的 N 款（实测 11 款候选）。

> ⚠️ **口径必须诚实（PRD §5 同类约束）**：Steam **不返回实付价**，所以只能叫
> 「**库当前商店价**」，**绝不能叫「你一共花了多少钱」**。界面要写明这是「按当前商店价估算」。
> 这条做错就是「用看起来像的数据糊过去」，正是 PRD 明确禁止的。

**规模感**：小（一个 `libraryValue()` 纯函数 + 一张卡片）。落点建议放游戏库页顶部。

### N1-2　游戏库补「类型 / 标签」筛选

**实测覆盖度**：66 款有 `genres`、67 款有 `tags`（仅 2–3 款缺，不影响功能）。

**为什么**：`LibraryPage.tsx:29-40` 的 `FILTERS` 只有
`全部 / 玩过 / 还没玩 / 有成就 / 已全成就` 五个维度，**没有任何类型 / 标签筛选**；
而 `WishlistPage.tsx:67-71, 134-146` 早就做了标签筛选 —— **两边明显不对称**。

**建议做法**：把愿望单页那套标签按钮（按出现频次取 TOP 10）搬到游戏库，
再加一个「类型」下拉（genres 的取值比 tags 少得多，适合下拉）。

**规模感**：小（照抄愿望单页的实现）。

---

### N1-3　「我拿到的最稀有成就」榜

**实测**：`achievements` 共 4536 条，其中 `is_rare = 1` 有 **2698 条**，`rare_locked = 2652`。

**为什么**：成就追猎页展示的是**未解锁**的稀有成就（2652 个）；
成就中心的三个板块是「最近解锁 / 即将完成 / 待解锁」——
**「我已经拿到的稀有成就」反而没有任何地方能看到**，而这是玩家最想炫耀的东西。

**建议做法**：成就中心加一个「最稀有成就 TOP N」（按 `global_percent` 升序，只取 `unlocked = 1`），
或直接做成可分享的小卡片（复用 Wrapped 的导出链路）。

**规模感**：小（排序 + 一个列表组件）。

---

### N1-4　游戏对比（2–4 款并排）

**数据齐**：时长 / 成就完成度 / 好评率 / 价格全在 `games` 表里。

**为什么**：实测 **11 款买了没玩**，用户真实的决策问题是「先玩哪个」；
现在只能一款一款点进详情页来回翻。

**规模感**：中（一个对比表 + 选择器 UI）。

## Tier 2 · 第一印象与操作效率

### N2-1　「每日时长还没积累」的等待期引导　⭐

**实测痛点**：`play_sessions` 表 **0 行**。

新装用户同步完 69 款游戏、4392 小时累计时长之后，游戏分析页的
**「每日游玩时长」「游戏时间热力图」「常玩时段分布」「最近 30 天趋势」四张图会同时是空状态**。

**现状**：空状态文案已经解释了原因（「需要至少两次跨天同步」），
但**没有任何「还要等多久」「进度到哪了」的反馈** —— 用户不知道明天再开一次就好了。

**建议做法**：

- 在空状态里加一行明确的时间预期（「下次跨天同步后自动点亮」）；
- 或者更实在：把**不依赖差分**的视图（`playtime_forever` 总时长排行、好评率排行）在空状态下**前置展示**，
  让用户第一次打开就有东西看。

**规模感**：小（改文案 + 调整空状态下的展示顺序）。

---

### N2-2　全局搜索 / 命令面板（Ctrl+K）

**现状**：全仓只有一个 `keydown` 监听（`TitleBar.tsx:55`），没有任何全局搜索。

**为什么**：69 款游戏想直达某款，只能先点「游戏库」再在页内搜；跨页跳转（去愿望单 / 去设置某一节）也全靠点。

**规模感**：中（一个浮动面板 + 路由索引）。

---

### N2-3　键盘快捷键

Esc 返回上一页、列表 ↑↓ 选择、Enter 打开。成本极低，桌面应用该有。

## Tier 3 · 工程与分发（V1 遗留，仍未做）

| 项 | 实况（截至今日） |
| --- | --- |
| **代码签名** | 仍是 **0 签名**（V1 的 P0-3 未做）→ 朋友双击会撞 SmartScreen 蓝框 |
| **自动更新** | 仍未引入 `electron-updater`，每改一次都要重发 **117 MB** |
| **`games` 表缺 `steam_id`** | 多账号会互相覆盖（V1 的 P3-2，当前只在 UI 上说明「单账号」，未改表结构） |
| **`achievements` 单次 IPC 约 1.3 MB** | 实测 4536 行 = **1,347,640 字符**，`loadSnapshot()`（`repository.ts:191`）每次 reload 全量传渲染层 |

> 最后一条与 N0-1 是同一类问题（**快照全量返回**）。
> 根因是 `loadSnapshot()` 把 7 张表整表塞进一个 Snapshot 对象走 IPC。
> 如果想要更彻底：改成**按页取数**（各页面只取自己需要的表），但那是较大的重构，收益要等数据量真上来才明显。

## 仍然不建议做（与 PRD §5 一致，未变）

| 项 | 为什么不做 |
| --- | --- |
| 自建「每日游玩时长」数据源 / 引入第三方史低源 | Steam 官方不提供，第三方不可靠。宁可显示「需要积累」，也不用看起来像的数据糊过去 |
| 把 SQLite 换成联网后端 | 会让「无需账号、数据不出本机」这个优点消失 |
| 应用内实现 Steam 账号密码登录 | 已有 OpenID 走系统浏览器，安全模型正确，任何倒退都不做 |

---

## 如果只挑三件做

1. **N0-2 接上价格走势图** —— 20 行 JSX，把已经采了 1362 条的**死数据**变成可见功能，投入产出比最高。
2. **N0-1 给两张采样表加保留策略** —— 现在不做，一年后是上百万行；越晚做迁移越难。
3. **N1-1 库价值分析** —— 数据现成、用户一眼就懂，且能把「11 款买了没玩」这种真实痛点摆到台面上。
