## 一、结论摘要

用户报告的 4 类「空数据」，拆开看是**两类性质完全不同**的问题：

| 用户报告 | 真实根因 | 性质 |
| --- | --- | --- |
| ① 本周每日游戏时间空 | `play_sessions` 表 0 行 —— 首次同步只建立基线，需 ≥2 次同步且期间有游玩增量 | **设计限制**（非缺陷） |
| ② 最近 30 天趋势空 | 同上 | 设计限制 |
| ③ 游戏分析页多图空 | 同上（但「游戏时长排行榜」走 `playtime_forever`，**是有数据的**） | 设计限制 |
| ④ 折扣商城 3 个专区空 | 3 个**互相独立**的真缺陷 | **缺陷 ×3** |

此外巡查出 **7 个此前未知的缺陷**，其中 3 个影响面很大：游戏详情大面积丢失、成就全部没有名字、成就全部被误标「极稀有」。

## 二、R1（最严重）`appdetails` 顶层键与请求的 appid 不一致

### 现象

`steam-api.ts:170` 用请求的 appid 去取顶层键：

```ts
const entry = isObj(j) ? (j as Record<string, unknown>)[String(appId)] : undefined
if (!isObj(entry) || entry.success !== true) return null
```

### 实测证据

| 请求 | 返回的顶层键 | `data.steam_appid` | 结果 |
| --- | --- | --- | --- |
| `appids=3220060` | **`5166020`** | 3220060 | 取键失败 → `null` |
| `appids=2358720` | **`3288260`** | 2358720 | 取键失败 → `null` |
| `appids=246420` | `246420` | 246420 | 正常 |

`3288260` 正是黑神话悟空自己 `dlc` 数组里的 id。**Steam 服务端就是会返回错位的顶层键。**

**与本地环境无关**：用 curl 走 clash 代理（完全绕过 Steam++ 本地反代）返回**完全相同的错位键**，因此排除「加速器污染」这一可能。

### 影响面（真实数据库统计）

| 受影响数据 | 结果 |
| --- | --- |
| `games` 的 `developer` | **54 / 69 款为空** |
| `games` 的 `release_date` | **69 / 69 全空** |
| `games` 的 `genres` | 55 / 69 为空 |
| 愿望单 2 款 | **名字、价格全部为空**（`name=''`、`final_price_cents=-1`） |
| 折扣商城 | `specials` 返回 10 条，**只入库 4 条** |

### 被放大的原因

`repository.ts` 的 `upsert` 是 `ON CONFLICT DO UPDATE SET <全部列>`。某次同步取不到某字段时，会用**空值覆盖此前的好数据**——数据只会在同步中不断劣化，不会自愈。

## 三、折扣商城 3 个专区为空 —— 三条独立根因

### R2　「高评分折扣」恒空：好评率被硬编码为 0

`steam-api.ts:187-188`：

```ts
// 评测百分比需单独的 appreviews 接口，这里只取推荐总数；百分比在演示数据里才是真实的
reviewPercent: 0, reviewCount: asNum(...)
```

**但该接口实测完全可用**，只是没被调用：

| 游戏 | `total_positive` / `total_reviews` | 好评率 | Steam 描述 |
| --- | --- | --- | --- |
| 黑神话：悟空 | 1,169,841 / 1,212,487 | **96%** | 好评如潮 |
| Kingdom Rush | 16,836 / 17,316 | **97%** | 好评如潮 |
| The Last of Us Part II | 50,705 / 55,768 | **91%** | 特别好评 |

接口：`store.steampowered.com/appreviews/{id}?json=1&language=all&purchase_type=all&num_per_page=0` → `query_summary.total_positive / total_reviews`。

### R3　「限时免费」恒空：判定逻辑不可能产出结果

`sync.ts:136` 从**打折商品列表**里筛免费：

```ts
if (s.isFree) discounts.push(mkDiscount(s, 'free', now))
else if (s.priceCents >= 0 && s.originalPriceCents > s.priceCents) discounts.push(...)
```

`specials` 全部是**有折扣**的商品，而「打折」与「免费」互斥 —— 该分支**永远不可能命中**。

同时实测 `featuredcategories` 共 13 个分类：`specials`(10) / `top_sellers`(10) / `new_releases`(30) / `coming_soon`(10) / 数字键 0–6 —— **其中没有 free 分类**。数字键 `3` 是「免费周末」活动，与「限时免费领取」不是同一概念。

> **结论**：实时模式下「限时免费」**没有可靠数据源**。诚实的做法是保留空状态并说明，或改名为「当前免费 / 免费周末」。

### R4　「史低专区」恒空：折扣商品从不进入价格采样

`mkDiscount()` 硬编码：

```ts
isHistoricalLow: false, historicalLowCents: -1,
```

而 `price_history` 的采样循环只遍历**游戏库**（`for (const g of games)`），折扣商品从不写入 → 史低**永远算不出来**（不是「首次为空、后续会有」）。

## 四、成就模块三连缺陷

### R5　不传 `l` 参数 → Steam **不返回** name / description

`steam-api.ts:124` 未传 `l`：

```ts
apiUrl('/ISteamUserStats/GetPlayerAchievements/v1/', { steamid: steamId, appid: String(appId) })
```

实测对比（同一游戏、同一时刻）：

| 请求 | `nonEmptyName` | 第一条原始返回 |
| --- | --- | --- |
| **不传 `l`** | **0 / 147** | `{"apiname":"WIN_BOMB_PLANT","achieved":0,"unlocktime":0}` |
| `&l=schinese` | **147 / 147** | 多出 `"name":"帮我们安置炸弹","description":"通过安置炸弹赢得一局"` |

字段是**整个不存在**，不是空字符串。→ 4536 条成就的名字与描述全部落库为空。

### R6　字段名写错：`desc` 应为 `description`

```ts
description: asStr(o.desc),   // ← 实际字段是 description
```

实测返回体的键为 `["apiname","achieved","unlocktime","name","description"]`，**没有 `desc`**。

### R7　`percent` 是字符串，被 `asNum` 丢成 0

```ts
function asNum(v: unknown, d = 0): number { return typeof v === 'number' ? v : d }
```

实测 `GetGlobalAchievementPercentagesForApp` 返回：

```json
{"name":"GIVE_DAMAGE_LOW","percent":"63.0"}     ← typeof percent === "string"
```

→ 4536 条成就的 `global_percent` 全部为 0。

**连带后果**：`isRare = pct < 10` 因此恒成立 → **所有成就都被标成「极稀有」**，界面出现「全球 0.0% 玩家拥有」的荒诞文案。

### R10（附带）成就图标恒空

代码硬编码 `iconUrl: ''` / `iconGrayUrl: ''`。而图标 URL 是**公开可推导**的，无需额外 API：

```
https://cdn.cloudflare.steamstatic.com/steamcommunity/public/images/apps/{appid}/{apiname}.jpg
```

界面因此全部退回灰色奖杯占位图。

## 五、R8 时间戳单位不一致

`utils/format.ts`：

```ts
export function formatDateTime(input) { const d = new Date(input * 1000) ... }   // 假设「秒」
```

主进程 `sync.ts` 广播的却是**毫秒**：

```ts
const t = Date.now()
update({ ..., lastSyncAt: t, ... })
```

毫秒 × 1000 → 年份溢出 → 设置页显示「上次同步 **58705-10 12:13**」。

同一原因使 `formatRelative` 收到毫秒值时算出巨大负数，恒满足 `diff < 60` → **无论多久前同步都显示「刚刚」**。

> 佐证：`bridge.ts` 的预览模式用的恰恰是 `Math.floor(Date.now()/1000)`（秒）—— 主进程与预览桥不一致，说明是主进程侧写错。

## 六、R9 `play_sessions` 为 0 —— 设计限制（非缺陷）

`sync.ts` 的快照差分逻辑**本身是正确的**（先 `lastSnapshot` 读基准，再 `saveSnapshot` 写本次）：

```ts
const prev = repo.lastSnapshot(g.appId)
repo.saveSnapshot(g.appId, todayStart, g.playtimeForeverMin)
if (prev !== null && g.playtimeForeverMin > prev) { sessions.push({ ... }) }
```

真实数据库状态：

| 项 | 值 | 含意 |
| --- | --- | --- |
| `snapshots` 行数 | 69（= 游戏数） | 每款游戏一次采样 |
| `snapshots` 的不同 `captured_at` | **1** | **只同步过一次** |
| `play_sessions` | 0 | 只有基线，没有可差分的增量 |
| `sqlite_sequence.play_sessions` | **10104** | 演示模式曾写入 10104 条，切到 API 模式后被 `clearAll()` 清空（序列号保留） |

**结论**：这不是代码错误。Steam 官方 API 不提供每日时长，只能靠「同步 → 游玩 → 再同步」逐步积累。
但**首次使用体验是全空**，这本身是产品问题（见第八节改进建议）。

**另一处隐患**：`settings.json` 里 `enableDemoData: true` 且已有 API Key → 走 `api` 模式，
而 `persist(data, full=false)` 时**不清空**演示数据 → 旧的演示数据会与真实数据混在一起残留。

### 仍未解决（不是缺陷，是事实）

1. **每日时长曲线仍需积累**：`play_sessions` 依赖快照差分，首次同步只建立基线。这是 Steam 官方 API 的固有限制，
